# 两轮体检：发现了什么，修了什么，我判断错过什么

这套东西是先用起来、再回头审的。跑通之后我做了两轮体检：翻源码、翻日志、
把 VS 的配置文件扒出来看、对跑着的 Ollama 直接发请求。

两轮下来一共改了 10 处。中间我自己也判断错过三回，都写在下面了。
排查一个"看起来在正常工作"的系统，最容易犯的错就是相信自己上一轮的结论。

## 怎么测的

原则是只认能复现的证据：

- 读代理源码和日志。日志里混了好几个开发版本的输出，所以我先给它加上时间戳才看得清；
- 读 VS 的 BYOM 配置实体文件，而不是看界面；
- 对跑着的 Ollama 直接发请求，用 `usage` 里的真实 token 数说话；
- 同一道题在改动前后各测一次，而且基线一起测；
- 每个结论都标清楚是实测还是推断。

## 第一轮：6 个问题

| # | 问题 | 证据 | 怎么修的 |
|---|---|---|---|
| 1 | 检索词用整句话，搜索引擎抓不住重点 | 整句检索返回 Python 官网、下载页、菜鸟教程，0/5 相关；抽报错原文是 5/5 正解 | 新增 `extract_search_query()`，报错原文优先，抽不到才退回整句清洗 |
| 2 | 注入无关网页，还命令模型必须引用 | 问 `ModuleNotFoundError: No module named requests`，注入的正文是一篇 2500 字的《Windows 下如何安装 Python》 | 加相关性闸门，加"搜不到就说搜不到"的降级路径，重写注入块的指令 |
| 3 | 按域名重排是帮倒忙 | `_tech_score` 把 `csdn.net` 和 `stackoverflow.com` 打成了同样的 10 分，内容农场因此被顶成正文页 | 删掉重排，改成内容农场黑名单加字面相关性打分 |
| 4 | 注入块没有时间锚点 | VS 每条消息都带 `<current_datetime>`，代理把它剥掉了却没把日期放回去，模型没法判断"最新版本"是不是最新 | 注入块里加上检索时间戳 |
| 5 | 触发太激进，87.5%（56/64） | 兜底是 `return True`，"解释一下什么是 MoE 架构"这种纯知识题也会搜 | 纯概念题跳过，另加 `[search]` 强制开关 |
| 6 | 抓正文没有硬超时，日志也没有时间戳 | 实测某个 URL 的 `urlopen` 挂了 145 秒才返回 0 字符（timeout 不覆盖 DNS 解析）；日志混了好几个版本，没法归因 | 抓取放进线程池，限时 8 秒；日志加时间戳和每步可归因的字段 |

同一轮还顺手把官方推荐的采样参数写进了模型 tag：
`temperature=0.7 / top_p=0.8 / top_k=20 / repetition_penalty=1.05`。
在这之前 `ollama show --parameters` 是空的，跑的一直是 Ollama 的内置默认值。

## 第二轮：4 个问题

第一轮我只测了 `stream:false` 的简单请求。VS 的真实路径是 `stream:true` 加 26 个 agent 工具，
还有多轮工具往返。按真实路径复测，又挖出 4 个问题，其中 1 个是我第一轮自己弄出来的。

| # | 问题 | 证据 | 怎么修的 |
|---|---|---|---|
| 1 | 标签剥离会删掉用户自己的代码 | `把 <T> 改成 List<T> 怎么做` 变成 `把  改成 List 怎么做`；`<b>粗体</b> 和 <i>斜体</i> 标签怎么用` 变成 `和  标签怎么用` | 从"删掉所有标签"改成只剥 VS 注入的那些，用显式白名单加 `小写_下划线` 命名模式 |
| 2 | 闸门把正常 query 滤空了（第一轮引入的） | 14 条真实 query 里 5 条完全为空；"今天有什么重要的AI科技新闻" raw=8 而 kept=0；总体 keep 率只有 20% | 时效类阈值降到 0.15，另加"永不滤空"：最高分大于 0 就留那一条并标注低置信度 |
| 3 | 延续消息触发完整搜索 | `继续`、`好的`、`还有吗`、`分析一下`、`谢谢` 全部 `search=True`，检索词就是"继续"两个字 | 新增 `_CONTINUATION_RE` |
| 4 | agent 每轮工具往返都重跑搜索 | 三轮对话等于三次搜索（日志里 7→8→9→10） | 新增按检索词的结果块缓存，TTL 300 秒。实测降到一次搜索加两次命中 |

修完之后的验收：

| 项目 | 改之前 | 改之后 |
|---|---|---|
| 用户代码会不会被删 | `<T>`、XML、`<b>` 全被删掉 | 全部保留，而且真实 VS 消息仍然精确得到 `你能联网吗` |
| 闸门 keep 情况 | ok=9，empty=5（共 14 条） | ok=12，weak=1，empty=1 |
| 延续消息 | 6 条触发搜索 | 全部不搜，同时"苹果股价多少"没有被误伤 |
| 三轮 agent 对话 | 3 次搜索 | 1 次搜索加 2 次缓存命中，作答轮仍然引用 `[S1]` |

这一轮还顺手验证了几件本来担心的事，确认没问题，记下来省得以后再怀疑一遍：

- 真实 VS 请求形态（25069 字符系统提示加 26 个工具加 10 轮历史）全链路通过：
  `HTTP 200`、`text/event-stream`、17.47 秒、引用了 `[S1]`、结构完整。
- 模型确实在遵守新的注入规则，回答稳定是"判断依据、结论、仍不确定的点"这个结构。
- 流式加 26 个工具的 `tool_call.index` 正确递增。网上传的 Ollama issue #16212 在 0.35.1 上没复现。
- 长上下文捞针（16738 tokens）精确命中。

## 三处自我更正

### 一、"`web-search-mcp.py` 的 stdout 重包装会让 `print` 崩溃"

这是我说的，错的。干净实验证明 `sys.__stdout__` 持有原 wrapper 的引用，缓冲区不会被关掉，
单次加载下 `print` 和 `sys.stdout.write` 都正常。

真因是我的探针把那个模块加载了两次，一次是我自己加载，一次是 `ollama-proxy.py` 内部又加载了一遍。
第二次包装让第一个 wrapper 引用归零、被垃圾回收关掉，连带把共享缓冲区也关了。
我用"连续包装两次"复现出了 `ValueError: I/O operation on closed file`，机制确认。

那个文件本身没问题，我没动它。教训是探针脚本自己也会制造假象。

### 二、"超出 `num_ctx` 时 Ollama 会静默截断 prompt"

也是错的。实测 9381 tokens 对 `num_ctx=4096`、38131 tokens 对 `num_ctx=32768`，
两次都是 `HTTP 400 exceed_context_size_error`，报错，不截断，不丢数据。

我怎么会得出这个错结论：当时看到一个请求的 `prompt_eval_count=64,948`，
而它的输入是 91939 个字符。我用"字数乘 0.77"估算 token 数，得出来大约 68K，超过 65536，
就以为被截断了。实际上 64948 就是它真实的 token 数，根本没超，也没截断。
我把自己的估算误差当成了实测发现。

### 三、"prefill 速率随上下文长度退化，508 → 169 → 94 tok/s"

这个结论同样不成立。同一个 9K prompt 在重载之后复测，是 18.39 秒变成 6.10 秒，
然后又变成 2.30 秒和 2.42 秒。

之前那批"随长度单调下降"的数据里混了两样东西：连续重载导致的降频，以及前缀缓存。
可信的只剩量级（38K 大约 248 秒，65K 大约 694 秒），具体数字受机器热状态影响太大，
不能当规格用。

教训是看到"性能随某个变量单调变化"的时候，先怀疑测试顺序和机器状态，再怀疑那个变量。

## 试过但没用的方案

让 4B 小模型当"检索路由器"，也就是让模型决定该不该搜、把用户问题改写成检索词。
设计上可行，社区也有人这么做，但代价是每次多一次模型调用，而且小模型时不时吐出空的或很烂的检索词。
现在的死规则虽然笨，但快、可预测、出了问题一眼能看懂。所以没做。

"只删掉重排就够了"也不对。旧的 `_tech_score` 只对编程类 query 生效，非编程 query 走的是
搜索引擎的原始顺序，两条路都可能给出无关结果。删重排和加闸门必须一起做。

`site:stackoverflow.com` 这个操作符在 cn.bing 上没用，直接被忽略，返回结果和不用时一模一样。

## 回滚

代理是单文件，回滚就是换文件再重启：

```powershell
Copy-Item proxy\ollama-proxy.py.bak-<时间戳> proxy\ollama-proxy.py -Force
# 然后重启：杀掉监听 11435 的 python，再跑 scripts\start-proxy.ps1
```

模型回滚，去掉采样参数回到 Ollama 默认：

```powershell
ollama create qwen3-coder:30b -f models/Modelfile.import-from-gguf
```

## 下次还会这么干

几条这轮踩出来的经验，留着自己看：

第一，测真实路径，别测简单路径。第一轮我测了 `stream:false` 就以为完事了，
而 VS 用的是流式加 26 个工具加多轮往返，第二轮那 4 个问题全藏在这里面。

第二，改完之后要专门回头测"改动本身有没有引入新问题"。第二轮的第 2 个问题就是我第一轮留下的坑。

第三，基线一定要一起测。说"联网慢 X 秒"就得同时给出不联网的数字，
不然机器状态的变化会被算成联网开销。

第四，别拿估算值当实测值。第二处更正就是这么来的。

第五，看到单调趋势先怀疑测试顺序。第三处更正就是这么来的。

第六，日志要能归因。没有时间戳、没有每步耗时字段的日志，等于没有日志。

第七，对自己上一轮的结论保持怀疑。这份文档里三处更正，全部是在"已经改好了"之后才发现的。
